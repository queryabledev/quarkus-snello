# Quarkus Snello

![Snello Logo](docs/images/snello-logo.svg)

[![Built with Maven](https://img.shields.io/badge/Built%20with-Maven-C71A36?logo=apachemaven&logoColor=white)](https://maven.apache.org/)
[![Quarkus](https://img.shields.io/badge/Quarkus-3.39.5-4695EB?logo=quarkus&logoColor=white)](https://quarkus.io/)
[![License](https://img.shields.io/badge/License-Apache%202.0-blue.svg)](https://www.apache.org/licenses/LICENSE-2.0)

Quarkus Snello brings the [Snello](https://github.com/snello-cms/snello-api) query
language to standard Quarkus + Hibernate ORM applications: every JPA `@Entity` is
automatically exposed as a REST CRUD resource with a rich suffix-based filter
language (`price_lte=100`, `title_ilike=spring`, `or1.status=draft`...), **without
any annotation on the entities**.

## The Snello family: two philosophies, one query language

[Snello API](https://github.com/snello-cms/snello-api) is a **metadata-driven
headless CMS**: tables, fields and query behavior are modeled through metadata and
can be created and changed **at runtime**, without writing one controller per
business table.

**Quarkus Snello is the compile-time counterpart.** The same REST query syntax, but:

- the exposed tables are the **JPA entities compiled into the application** — the
  whole API surface is decided **before going to production**, at build time;
- the system does **not** extend at runtime: it is not possible to query tables
  that were not pre-configured as entities. A request to a non-mapped table is
  simply a `404`, and filterable fields are whitelisted from the JPA metamodel
  (unknown fields are ignored, never forwarded to the database);
- in exchange you get everything the Quarkus build gives you: type-safe filters
  coerced through the entity model, generated OpenAPI documentation, native-image
  support, and no metadata storage to administer.

Choose Snello API when the data model must evolve at runtime; choose Quarkus
Snello when the model is owned by your codebase and you want the same ergonomic
query language on top of it.

Standard CRUD, count, OpenAPI and transaction handling are generated by
[Hibernate ORM REST Data with Panache](https://quarkus.io/guides/rest-data-panache/).
Quarkus Snello contributes the collection `GET` endpoint and its query language.

## Install

```xml
<dependency>
    <groupId>dev.queryable</groupId>
    <artifactId>quarkus-snello</artifactId>
    <version>1.0.0</version>
</dependency>
```

Applications also select their JDBC driver and JSON extension, for example
`quarkus-jdbc-postgresql` and `quarkus-rest-jackson`.

Full documentation lives in the [docs module](docs/modules/ROOT/pages/index.adoc).

### Building and testing

```bash
mvn install                                 # build + JVM tests
mvn verify -DskipITs=false                  # also run the suite against the packaged app
mvn verify -Dnative                         # also build the native image and test it (requires GraalVM or a container runtime)
```

## How entities are exposed

Each concrete `@Entity` is exposed at `<base-path>/<table name>`:

```java
@Entity
@Table(name = "articles")
public class Article {
    @Id @GeneratedValue
    public Long id;
    public String title;
    public String status;
    public BigDecimal price;
    public LocalDate published_at;
}
```

→ `GET/POST /api/articles`, `GET/PUT/DELETE /api/articles/{id}`, `GET /api/articles/count`.

- The path segment is the `@Table(name = ...)` value; without `@Table` it falls back to the
  lowercase entity name.
- Annotate an entity with `@SnelloExclude` to keep it out of the REST exposure.
- The base path is configurable with `quarkus.snello.base-path` (default `/api`);
  setting it to `/` exposes the entities directly at the root (`/articles`). The
  standard Quarkus `quarkus.http.root-path` (default `/`) is applied on top of it,
  as for every HTTP endpoint: with `quarkus.http.root-path=/myapp` the resource
  becomes `/myapp/api/articles`.
- `quarkus.snello.default-limit` (default `0` = unlimited) caps plain listings when
  `_limit` is absent; an explicit `_limit` always wins, including `_limit=0` for an
  unlimited result.
- Every scalar persistent field is filterable (numbers, strings, booleans, dates, UUIDs,
  enums). Associations are not traversed: filter on the foreign key column instead.
- Field and operator are separated by the **last** `_` of the parameter key:
  `published_at_gte=2024-01-01` filters field `published_at` with operator `gte`. When the
  trailing segment is not a known operator the whole key is matched as a field name
  (`team_id=1` is an equality filter on `team_id`).
- Unknown parameters are ignored; invalid values and unknown sort fields return `400`.
- Collection responses carry the `X-Total-Count`, `X-Start` and `X-Limit` headers.
- `select_fields=id,title` projects the response to the listed fields only (unknown
  fields return `400`); filters, sorting and pagination still apply.

## Securing the generated endpoints

Snello does not ship its own security layer: the generated resources are regular
JAX-RS endpoints, so the standard
[Quarkus HTTP security policies](https://quarkus.io/guides/security-authorize-web-endpoints-reference)
apply to them. For example, with basic authentication and
`quarkus-elytron-security-properties-file`:

```properties
quarkus.http.auth.basic=true

quarkus.http.auth.permission.developers.paths=/api/developers/*
quarkus.http.auth.permission.developers.policy=authenticated
quarkus.http.auth.permission.developers-list.paths=/api/developers
quarkus.http.auth.permission.developers-list.policy=authenticated
```

Both the snello collection `GET` and the CRUD endpoints generated by REST Data with
Panache are covered: unauthenticated requests get `401`. Role-based policies
(`quarkus.http.auth.policy.*.roles-allowed`) and any other Quarkus identity provider
(OIDC, JWT, JDBC...) work the same way.

## OpenAPI

With `quarkus-smallrye-openapi` on the classpath, each generated collection endpoint
documents its query parameters in a type-aware fashion — every scalar field is
expanded with the filter suffixes that make sense for its type:

| Field type | Documented parameters |
|---|---|
| any scalar | `field`, `field_ne`, `field_in`, `field_nn`, `field_inn` |
| `String` | + `field_contains`, `field_like`, `field_ilike`, `field_containss`, `field_rlike`, `field_llike`, `field_ncontains`, `field_nie`, `field_ie` |
| numbers, dates, chars | + `field_lt`, `field_lte`, `field_gt`, `field_gte` |
| booleans, enums, UUIDs | base set only |

The reserved parameters (`_start`, `_limit`, `_sort`, `select_fields`) are documented
on every collection endpoint. OR-group parameters (`or{N}.…`) are dynamic and are
not listed individually. At runtime every documented parameter — and the OR-group
variants — is parsed from the request; the engine itself remains permissive and is
not limited to the documented set.

## REST lifecycle and validation

Implement `SnelloRsListener<T>` as a CDI bean to observe or validate the generated
endpoints. Before-callbacks can reject the operation by throwing a REST exception;
after-callbacks run once the transaction has committed.

```java
@ApplicationScoped
public class ArticleListener implements SnelloRsListener<Article> {

    @Override
    public void onBefore(SnelloEvent<Article> event) {
        if (event.operation() == SnelloOperation.CREATE && event.entity().orElseThrow().title == null) {
            throw new BadRequestException("Title is required");
        }
    }

    @PostPersist
    void created(Article article) {
        // audit, notifications, cache invalidation...
    }
}
```

Annotated callback methods are supported for every operation: `@PreFetch`/`@PostFetch`,
`@PreList`/`@PostList`, `@PrePersist`/`@PostPersist`, `@PreUpdate`/`@PostUpdate`,
`@PreDelete`/`@PostDelete`. The single optional parameter can be the `SnelloEvent`,
the entity, the result `List` or the entity id.

## Custom Criteria filters

Implement `SnelloFilter<T>` as a CDI bean to contribute extra `CriteriaBuilder`
predicates to the collection query. Contributed predicates are combined in `AND`
with the suffix filters and also apply to the total count.

```java
@ApplicationScoped
public class ArticleSearchFilter implements SnelloFilter<Article> {

    @Override
    public void contribute(SnelloFilterContext<Article> context) {
        String search = context.param("search");
        if (search != null && !search.isBlank()) {
            var cb = context.criteriaBuilder();
            var root = context.root();
            String pattern = "%" + search.toLowerCase() + "%";
            context.add(cb.or(
                    cb.like(cb.lower(root.get("title")), pattern),
                    cb.like(cb.lower(root.get("description")), pattern)));
        }
    }
}
```

### Relations

Snello deliberately does **not** traverse JPA associations: entities are meant to be
flat, with foreign keys mapped as plain scalar columns (`team_id`, not
`@ManyToOne Team team`). This keeps the query language unambiguous, avoids
accidental joins and N+1 surprises, and lets every column be filtered with the
standard suffixes (`?team_id=1` just works).

When you do need to filter through a relation, resolve it with a custom filter and
a subquery — `SnelloFilterContext.query()` exposes the criteria query exactly for
this:

```java
@ApplicationScoped
public class ArticleTeamFilter implements SnelloFilter<Article> {

    @Override
    public void contribute(SnelloFilterContext<Article> context) {
        String teamName = context.param("team_name");
        if (teamName == null || teamName.isBlank()) {
            return;
        }
        Subquery<Long> teams = context.query().subquery(Long.class);
        Root<Team> team = teams.from(Team.class);
        teams.select(team.get("id"))
                .where(context.criteriaBuilder().equal(team.get("name"), teamName));
        context.add(context.root().get("team_id").in(teams));
    }
}
```

→ `GET /api/articles?team_name=backend` becomes
`WHERE team_id IN (SELECT id FROM team WHERE name = 'backend')`, combinable with any
other filter and reflected in `X-Total-Count`.

# REST Query Params

This page explains how to use HTTP query parameters to filter, sort, and paginate data when querying metadata records via the REST API.

The filtering system is based on **field name suffixes** appended to a query parameter key. Each suffix maps to a specific SQL condition applied in the database `WHERE` clause.

---

## Pagination & Sorting

These are reserved parameters that control the result set shape.

| Parameter | Description | Example |
|---|---|---|
| `_limit` | Maximum number of records to return | `_limit=10` |
| `_start` | Offset (zero-based) of the first record to return | `_start=20` |
| `_sort` | Sort field and direction (`field:asc` or `field:desc`) | `_sort=created_at:desc` |
| `select_fields` | Comma-separated list of fields to include in the response | `select_fields=id,name,email` |

**Example — paginated and sorted request:**
```
GET /api/datalist/metadata/articles?_limit=10&_start=0&_sort=published_at:desc
```

---

## Filter Suffixes

Append a suffix to the **field name** to specify the type of SQL condition to generate.

### Equality (default)

No suffix needed. A plain field name matches records where the field equals the given value.

| Suffix | SQL operator | Description |
|---|---|---|
| *(none)* | `=` | Exact match |

**Example:**
```
GET /api/datalist/metadata/articles?status=published
```
→ `WHERE status = 'published'`

---

### Comparison

| Suffix | SQL operator | Description |
|---|---|---|
| `_ne` | `!=` | Not equal |
| `_lt` | `<` | Less than |
| `_lte` | `<=` | Less than or equal |
| `_gt` | `>` | Greater than |
| `_gte` | `>=` | Greater than or equal |

**Examples:**
```
GET /api/datalist/metadata/products?price_lt=100
```
→ `WHERE price < 100`

```
GET /api/datalist/metadata/products?price_gte=50&price_lte=200
```
→ `WHERE price >= 50 AND price <= 200`

```
GET /api/datalist/metadata/orders?status_ne=cancelled
```
→ `WHERE status != 'cancelled'`

---

### LIKE / Pattern matching

| Suffix | SQL operator | Value wrapping | Description |
|---|---|---|---|
| `_contains` | `LIKE` | `%value%` | Contains substring (case-sensitive) |
| `_like` | `LIKE` | `%value%` | Alias of `_contains` |
| `_ilike` | `ILIKE` | `%value%` | Contains substring (case-insensitive, PostgreSQL) |
| `_containss` | `LIKE lower()` | `%lower(value)%` | Contains lowercase substring (lowercases both sides) |
| `_rlike` | `lower(field) LIKE lower(?)` | `value%` | Starts with value (case-insensitive) |
| `_llike` | `lower(field) LIKE lower(?)` | `%value` | Ends with value (case-insensitive) |
| `_ncontains` | `NOT LIKE` | `%value%` | Does **not** contain substring |

**Examples:**

For `_rlike` and `_llike`, right/left refers to the position of the `%` wildcard.
Both sides are lowercased by the database for case-insensitive matching on PostgreSQL, MySQL, and H2.
These filters previously used case-sensitive `LIKE` without lowercasing; wildcard directions are unchanged.

```
GET /api/datalist/metadata/articles?title_contains=spring
```
→ `WHERE title LIKE '%spring%'`

```
GET /api/datalist/metadata/users?email_ilike=gmail
```
→ `WHERE email ILIKE '%gmail%'`

```
GET /api/datalist/metadata/products?code_rlike=SKU
```
→ `WHERE lower(code) LIKE lower(?)`, with bound parameter `SKU%`

```
GET /api/datalist/metadata/logs?message_ncontains=debug
```
→ `WHERE message NOT LIKE '%debug%'`

---

### IN list

| Suffix | SQL operator | Description |
|---|---|---|
| `_in` | `IN (...)` | Field value is one of a comma-separated list |

**Example:**
```
GET /api/datalist/metadata/articles?status_in=draft,published,review
```
→ `WHERE status IN ('draft', 'published', 'review')`

---

### NULL checks

These suffixes do **not** require a value — the parameter key alone is sufficient.

| Suffix | SQL condition | Description |
|---|---|---|
| `_nn` | `IS NOT NULL` | Field has a value |
| `_inn` | `IS NULL` | Field has no value |

**Examples:**
```
GET /api/datalist/metadata/users?avatar_nn
```
→ `WHERE avatar IS NOT NULL`

```
GET /api/datalist/metadata/users?deleted_at_inn
```
→ `WHERE deleted_at IS NULL`

---

### Empty string checks

These suffixes do **not** require a value — the parameter key alone is sufficient.

| Suffix | SQL condition | Description |
|---|---|---|
| `_nie` | `<> ''` | Field is **not** an empty string |
| `_ie` | `= ''` | Field **is** an empty string |

**Examples:**
```
GET /api/datalist/metadata/articles?description_nie
```
→ `WHERE description <> ''`

```
GET /api/datalist/metadata/profiles?bio_ie
```
→ `WHERE bio = ''`

---

## Numeric field filtering

When filtering on a numeric column (e.g. `numeric`, `integer`, `bigint`, `decimal`), pass the value as a plain string — the API automatically casts it to the correct type before binding the prepared statement.

**Example** — table with column `heat_number numeric(10,0)`:
```
GET /api/ficr_results?heat_number=5
```
→ `WHERE heat_number = 5` (bound as a number, not a string)

No explicit cast is needed in the query parameter.

---

## Combining multiple filters

All filter parameters are combined with `AND`.

```
GET /api/datalist/metadata/products?category=electronics&price_gte=100&price_lte=500&status_ne=discontinued&name_ilike=pro
```
→
```sql
WHERE category = 'electronics'
  AND price >= 100
  AND price <= 500
  AND status != 'discontinued'
  AND name ILIKE '%pro%'
```

### OR groups

Prefix a parameter with `or{N}.` to combine it in `OR` with the other parameters of
the same `or{N}` group. Each group produces a single parenthesised condition that is
combined in `AND` with the other groups and the plain parameters.

```
GET /api/datalist/metadata/products?or1.category=electronics&or1.category=test&or2.price_gte=100&or2.price_lte=500&status_ne=discontinued
```
→
```sql
WHERE (category = 'electronics' OR category = 'test')
  AND (price >= 100 OR price <= 500)
  AND status != 'discontinued'
```

All the filter suffixes work inside a group, including the no-value ones:
`?or1.avatar_inn&or1.price_gte=150` → `WHERE (avatar IS NULL OR price >= 150)`.
Unknown fields inside an OR group return `400`.
