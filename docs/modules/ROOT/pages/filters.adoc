= Query parameters

The collection `GET` endpoint accepts filters built from field name suffixes:
the last `_` of a parameter key separates the attribute name from the operator.
When the trailing segment is not a known operator — or the leading segment is
not a filterable attribute — the whole key is matched as a field name with an
equality filter. For example `published_at_gte=2024-01-01` filters the field
`published_at` with `gte`, while `team_id=1` is an equality filter on `team_id`.

Unknown parameters are ignored; invalid values, unknown sort fields and unknown
projection fields return `400 Bad Request`.

== Pagination, sorting, projection

[cols="1,3,2"]
|===
|Parameter |Description |Example

|`_limit`
|Maximum number of records to return (`0` = unlimited)
|`_limit=10`

|`_start`
|Zero-based offset of the first record to return
|`_start=20`

|`_sort`
|Sort field and direction (`field:asc` or `field:desc`), comma-separated
|`_sort=created_at:desc`

|`select_fields`
|Comma-separated list of fields to include in the response
|`select_fields=id,name,email`
|===

`select_fields` projects the response to the listed fields only; filters,
sorting and pagination still apply, and `X-Total-Count` stays coherent.

== Filter suffixes

[cols="1,2,3"]
|===
|Suffix |SQL |Notes

|_(none)_ |`field = ?` |Exact equality
|`_ne` |`field != ?` |Not equal
|`_lt` |`field < ?` |Less than
|`_lte` |`field <= ?` |Less than or equal
|`_gt` |`field > ?` |Greater than
|`_gte` |`field >= ?` |Greater than or equal
|`_contains` |`field LIKE '%?%'` |Case-sensitive contains
|`_like` |`field LIKE '%?%'` |Alias of `_contains`
|`_ilike` |`lower(field) LIKE lower('%?%')` |Case-insensitive contains
|`_containss` |`lower(field) LIKE lower('%?%')` |Lowercases both sides
|`_rlike` |`lower(field) LIKE lower('?%')` |Case-insensitive starts-with
|`_llike` |`lower(field) LIKE lower('%?')` |Case-insensitive ends-with
|`_ncontains` |`field NOT LIKE '%?%'` |Case-sensitive not-contains
|`_in` |`field IN (?, ?, ...)` |Comma-separated values
|`_nn` |`field IS NOT NULL` |No value needed
|`_inn` |`field IS NULL` |No value needed
|`_nie` |`field <> ''` |No value needed
|`_ie` |`field = ''` |No value needed
|===

The case-insensitive variants are implemented with `lower()` on both sides, so
they behave identically on PostgreSQL, MySQL and H2.

Values are coerced to the field type before binding: numbers, booleans, dates
and times (ISO formats), UUIDs and enum constants all work without explicit
casts:

----
GET /api/articles?price_gte=50&price_lte=200&published_at_gte=2024-01-01
----

== Combining filters

All filter parameters are combined with `AND`:

----
GET /api/products?category=electronics&price_gte=100&price_lte=500&status_ne=discontinued
----

=== OR groups

Prefix a parameter with `or{N}.` to combine it in `OR` with the other
parameters of the same group. Each group produces a single parenthesised
condition combined in `AND` with everything else:

----
GET /api/products?or1.category=electronics&or1.category=test&or2.price_gte=100&or2.price_lte=500
----

[source,sql]
----
WHERE (category = 'electronics' OR category = 'test')
  AND (price >= 100 OR price <= 500)
----

All suffixes work inside a group, including the no-value ones. Unknown fields
inside an OR group return `400`.

== Custom Criteria filters

Implement `SnelloFilter<T>` as a CDI bean to contribute extra `CriteriaBuilder`
predicates to the collection query. Contributed predicates are combined in
`AND` with the suffix filters and also apply to the total count:

[source,java]
----
@ApplicationScoped
public class ArticleSearchFilter implements SnelloFilter<Article> {

    @Override
    public void contribute(SnelloFilterContext<Article> context) {
        String search = context.param("search");
        if (search != null && !search.isBlank()) {
            var cb = context.criteriaBuilder();
            var root = context.root();
            String pattern = "%" + search.toLowerCase() + "%";
            context.add(cb.or(
                    cb.like(cb.lower(root.get("title")), pattern),
                    cb.like(cb.lower(root.get("description")), pattern)));
        }
    }
}
----

The entity type is inferred from the generic parameter; override `entityType()`
when the generic type cannot be resolved.

== Relations

Snello deliberately does *not* traverse JPA associations: entities are meant to
be flat, with foreign keys mapped as plain scalar columns (`team_id`, not
`@ManyToOne Team team`). This keeps the query language unambiguous, avoids
accidental joins and N+1 surprises, and lets every column be filtered with the
standard suffixes (`?team_id=1` just works).

When you do need to filter through a relation, resolve it with a custom filter
and a subquery — `SnelloFilterContext.query()` exposes the criteria query
exactly for this:

[source,java]
----
@ApplicationScoped
public class ArticleTeamFilter implements SnelloFilter<Article> {

    @Override
    public void contribute(SnelloFilterContext<Article> context) {
        String teamName = context.param("team_name");
        if (teamName == null || teamName.isBlank()) {
            return;
        }
        Subquery<Long> teams = context.query().subquery(Long.class);
        Root<Team> team = teams.from(Team.class);
        teams.select(team.get("id"))
                .where(context.criteriaBuilder().equal(team.get("name"), teamName));
        context.add(context.root().get("team_id").in(teams));
    }
}
----

`GET /api/articles?team_name=backend` becomes
`WHERE team_id IN (SELECT id FROM team WHERE name = 'backend')`, combinable with
any other filter and reflected in `X-Total-Count`.
